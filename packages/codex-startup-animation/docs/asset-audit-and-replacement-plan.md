## 五、专业处理这项任务时需要补齐的关键工作

“顶尖专业人士”没有一份对所有团队统一的流程；本项目应按技术美术、渲染和macOS资源打包的实际责任来界定必要工作。

### A. 先确定实际消费者

不能用“文件存在”“命名像新版”判断在用。根目录image-settings.js没有被当前index.html加载，也未进入正式构建。旧⌘⌥B只属于旧extension renderer。

旧设置会把头像裁成512×512、背景裁成1536×1024，先铺不透明底再提取轮廓；它无法直接承担透明角色或新全景的替换。旧payload还组合新版根HTML/animation与旧AEMEATH_ASSETS，缺少当前AZHOU_WORKING_IMAGE，不能因代码还在就称为可恢复功能。

### B. 把图片与适配资料绑定

启动图的头、手、眨眼和尾巴坐标写在animation.js顶点着色器中。眼中心为(.491,.362)、(.608,.346)，手部中心(.558,.583)、(.624,.574)，头/颈及尾部也有独立区域。CSS角色位置、屏幕反馈、信号和粒子起点另有定位。替换同尺寸PNG不会自动重新校准这些位置。

准备脚本只检查PNG头、1254×1254、RGBA；虽然提示另一张图需要视觉审阅，代码没有自动完成姿态兼容判定。启动角色槽位必须接受与图像SHA匹配的校准包，不能凭同规格或一个approved:true字段通行。

### C. 防止源文件与派生结果脱节

现行build-macos.sh仅检查working.png/scene.js存在，再复制两者；没有校验JS内嵌图等于PNG。直接覆盖PNG可能构建成功而画面仍是旧图。当前两者实际一致，但替换流程存在缺口。

### D. 给“换的是哪套资产”一个明确标识

Native的wallpaper-status主要返回applied/imageDecoded/backgroundMatched等字段，不返回实际图片摘要。renderer回报的imageSHA256来自payload声明，未自行重算图像字节。

同软件版本换图后，旧壁纸仍可能是有效的applied:true。后续需按槽位记录selected/installed/live修订，修订覆盖图片、焦点或校准参数。软件版本不承担资产身份的职责。

### E. 划清构图与阅读标准

当前壁纸的横屏60%、窄窗88%焦点固定在CSS中。换成主体在左的图，即使字节和格式正确，也可能裁掉主体。需要有限焦点和主体区域配置，不能让用户每次手改CSS。

现有fixture正文使用96%宿主底色的阅读卡片，而真实页面正文可以直接叠在插画上。现有11组回归覆盖解码、样式、footer、回滚等，不包含文字后方局部像素对比度检测。这是视觉结论的明确缺口，不据此直接断言当前全部正文不合格。

### F. 说明输入摘要与回滚的真实边界

verify-artifacts.py当前把assets/private所有文件计入构建输入，包括未使用旧图和provenance。修改一张未选中候选或旧记录也会让来源摘要失配；这不等于当前画面损坏。后续应让候选先留在独立暂存位置；若采用显式依赖清单，仍须包含真正影响产物的源码、选定图、派生、校准、来源与选择配置。

现有回滚是局部的：构建载荷交换、应用包安装交换、页面样式候选分别有保护，但没有覆盖所有源文件/安装后登记/运行页的统一事务。prepare脚本顺序覆盖三个文件也不是成组提交。页面restore是恢复宿主原背景，不是恢复前一张壁纸。

## 七、外部依据与独立验收

1. **Apple资源签名。** [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)要求签名后的bundle作为只读资源处理。替换应从项目源资产经过重建/签名/统一安装；`codesign --verify --strict`证明包完整性，不能证明画面和身份正确。本项目为本地安装，不增加Developer ID、公证或公开发布任务。

2. **浏览器完整解码。** [MDN Image.decode](https://developer.mozilla.org/en-US/docs/Web/API/HTMLImageElement/decode)给出完成解码和损坏数据失败的语义。候选必须先完整解码，再进入正式选择；PNG头合法仍可能像素数据损坏。

3. **真实铺放。** [MDN background-size](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/background-size)明确cover等比铺满会裁切。[MDN devicePixelRatio](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio)区分CSS与设备像素。独立计算s=max(W/w,H/h)，设备放大比=s×DPR，裁切量=(w×s−W,h×s−H)，与实际计算样式和截图核对。

4. **阅读对比度。** [WCAG 2.2 1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum)给出正文4.5:1、大字号3:1的门槛；[W3C F83](https://www.w3.org/WAI/WCAG22/Techniques/failures/F83)要求检验文字后方实际图片区域。先用最不利背景快速检查，不通过时再检查实际字形位置。可将其用于本次壁纸可读性验收，不能由少量取样宣称整个宿主符合WCAG。

5. **独立提取与否证。** 写入manifest的程序不能成为唯一裁判。实际解码包内图像和当前Blob后重算摘要，故意提供同尺寸错姿态、损坏图片、不同步scene.js、假SHA等候选。多代理审查用于发现遗漏，不以“多数代理认为好看”作为外部证明。

“还是不是阿舟”及构图审美没有一个公共标准能完全自动裁决，应由正式原图/角色约定和独立审阅者对照。能机器验证的尺寸、字节、裁切、对比度与动作定位必须独立检验，不把美术判断扩张成无法证实的分数。

### 2. 使用方式

建议维护入口为项目中的一个轻量“更换阿舟素材.command”：选择类型与文件/已校准包，展示候选预览，点击一次“替换并应用”后自动完成后续动作。它是维护工具，日常启动入口仍是现有阿舟应用。

底层只需要一份共享资产清单、一个Python入口与公共校验/派生函数；命令形式可为`list / check / preview / apply`。所有入口复用同一实现。上述命令和文件名是设计建议，当前不能执行。

既有旧image-settings不复活；不做素材服务器、数据库、在线生成器、任意主题编辑器、字体/视频管理或第二个.app。

### 3. 一次操作的必要流程

1. 取得覆盖准备、构建、安装与复查的项目级操作锁；与安装器现有锁明确分工，避免嵌套自锁，直接构建也应检测冲突。
2. 将选定候选复制到忽略的暂存位置，固定字节摘要。预览与提交使用同一快照，外部原图始终只读。
3. 完整解码并检查本槽位契约；校准包必须绑定图片与校准内容，不接受仅靠approved布尔字段的包。
4. 自动生成派生资源并独立核验；一次记录源、派生、来源与配置的关系，用有限事务记录识别中断状态。
5. 调用现有统一构建/安装器，保留来源、符号链接、签名、版本、运行实例与唯一入口保护。
6. 从最终安装包检查实际资源；壁纸复用现有有限helper接入当前可核实页面，图标/启动角色执行各自专项验收。
7. 回报源选择、安装包、运行页三个位置的最终状态与槽位修订；本次操作结束，不新增常驻服务。

每个槽位的assetRevision应覆盖图像SHA和影响结果的配置/校准/派生规则版本。只改焦点也要改变壁纸修订；只换图标不要求重新应用无关壁纸。

### 4. 失败与生效状态

| 情况 | 对用户的准确结果 | 必须保持/核对 |
| --- | --- | --- |
| 候选解码/规格/校准不合格 | 未替换 | 活动源、安装和当前画面保持原状 |
| 源/派生提交中断 | 操作未完成，待恢复 | 下次可识别，不把混合文件当有效当前资产 |
| 构建失败或安装前失败 | 未安装；按事务恢复或报告具体未恢复项 | 不能只恢复一份源图就称全部回滚；核对源、隐藏载荷和安装包 |
| 安装交换后登记失败 | 已交换，但安装收尾未通过 | 记录实际包指纹和登记状态，不能笼统报旧版已恢复 |
| 安装成功、无可用连接端口 | 已安装，待正常重启应用 | 保留用户当前会话，不自动退出 |
| 页面重载/部分页面应用失败 | 已安装，当前应用未全部核实 | 分页面回报，不把一个成功页面代替全部 |
| 壁纸新图解码/样式提交失败 | 新安装存在，当前页保留原有效壁纸或明确失败状态 | 分别报告installed/live修订，允许重试 |
| 全链路核对成功 | 本槽位替换完成 | 实际使用资源与选定修订一致，专项验收通过 |

图标的系统缓存刷新、启动角色在下一次播放中的使用与壁纸当前页应用是不同生效时机。禁止承诺所有槽位都即时刷新已运行窗口。

现有三个局部回滚不能直接拼成跨文件/包/页面的全事务。首版只增加必要的源/派生成组提交及有限恢复记录，不建立持久旧.app或ZIP备份系统。

### 5. 建议实施顺序与完成门槛

| 阶段 | 最小改动 | 完成依据 |
| --- | --- | --- |
| 1. 共享契约与状态 | 引入统一三槽位定义；消除消费链的重复路径；显式活动依赖及槽位修订 | 当前三条资源输出保持一致；候选/旧记录改动不会被误当活动图片变化；来源保护保留 |
| 2. 壁纸与图标入口 | 暂存/检查/预览/自动派生，复用统一安装器和有限helper | 换图、只改焦点、同版本旧图、损坏图、安装待应用等反例能被识别 |
| 3. 启动角色包 | 提取现有校准为配置，绑定图片与关联定位 | 原默认完整播放保持；错图/错校准拒绝；只有经过完整动作验收的包允许切换 |
| 4. 中断与最终验收 | 有限事务记录、锁、各阶段失败结果，维护入口整合 | 在隔离环境复现中断/并发/登记失败；不会影响用户正式工作 |

不按换图次数升级软件版本来掩盖资产身份问题；只在实现代码改变时按项目版本规则升级。每次替换仅运行该槽位涉及的必要检查，避免换图标时重跑全部动画与壁纸测试。
