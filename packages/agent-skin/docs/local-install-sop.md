# Agent Skin 两端本地安装 SOP

用于维护者要求把最新源码安装到本机 Codex 和 DeepSeek Harness（DSH）的场景。“两端”指 Agent Skin 的两个宿主，不是 pstack 的安装目标，也不是更新官方宿主应用。

按本机现有环境执行，独立账户、虚拟机和隔离 profile 不是前置。仓库开发仍遵循 [Treehouse 工作区规则](../../../docs/worktree-policy.md)。本页组织现有工具和人工步骤，不提供统一安装命令，也不建立 Release、自动更新或公开分发流程。

## 1. 固定本次安装对象

1. 核对远端默认分支、本地提交与未提交改动。未指定分支时，“最新”取开始执行时核实的远端 main 提交；指定开发分支时明确记录为开发候选。不要从有无关改动的目录直接打包。
2. 记录完整提交号、构建输入摘要、宿主版本、两端安装位置和已运行实例。版本号/build 相同不证明内容相同；旧日志不证明当前页面运行的是新载荷。
3. 复用仍归本任务所有的工作区，或按仓库规则取得租约。确认私有素材和构建预检输入齐全；保留 [上游与素材权限边界](../UPSTREAM.md)。
4. 读取现有来源标记、安装回执和设置归属。DSH 将插件链接解析到实体目录，并列出所有共用该目录的 profile；一次目录更新会同时影响它们。

完成条件：两端各有明确的源码、产物、安装目标与受影响范围。缺少输入或归属不明的端保留旧安装，其他端可以继续，最终分别报告。

## 2. 构建并验证候选

在仓库根目录运行 `python3 scripts/verify.py`。下面命令从 `packages/agent-skin/` 执行，构建不会替换日常入口：

```sh
bash tools/build-macos.sh
python3 tools/verify-artifacts.py
python3 -B tools/build-dsh-plugin.py
python3 tools/verify-artifacts.py --verify-dsh-plugin .build/azhou-dsh-plugin/azhou-agent-skin
```

固定两端最终载荷摘要；应用还需签名验证。构建后源码、素材或产物变化，重新验证受影响的对象。功能与覆盖率门禁沿用 [testing.md](testing.md)；仓库检查、构建成功、模拟测试均不替代真实宿主验收。

完成条件：每个准备安装的候选通过对应构建校验，且可追溯到本次固定输入。

## 3. 按宿主执行安装

### Codex：正常升级与来源恢复

同一有效来源的正常安装：

```sh
python3 tools/install-macos.py
python3 tools/install-macos.py --check
```

跨来源且旧目录、回执、载荷仍完整时，按 [安装生命周期](installation-lifecycle.md#从旧项目目录接管现有安装) 使用 `--migrate-from`，再执行 `--check`。

旧来源已不存在时，进入该约定的人工恢复分支：核对本次授权覆盖的精确旧入口，验证身份、签名和完整指纹，保留并核验完整旧包，使用现有安装锁、暂存校验、原子替换与失败回滚；随后由原生安装器建立当前记录并复查唯一入口。已有明确目标授权可沿用；来源或目标仍不明确时先解决歧义。

这不是普通安装器已支持的自动选项。不要伪造旧回执、修改旧来源标记来通过检查，也不要先删旧入口。恢复记录保留旧目标、新旧摘要、备份位置和结果。

完成条件：`--check` 确认新载荷一致、实体和登记入口唯一。正在运行的 Codex 页面仍可能是旧版。

### DSH：校验实体包，再更新现有插件

首次安装使用官方插件机制，命令与宿主入口见 [DSH 插件合同](dsh-plugin.md) 和 [官方安装记录](../../../evidence/live-dsh-plugin-install-2026-11-05.md)。已有安装先确认由插件管理器管理，还是通过 profile 工作区链接运行；按实际安装所有者更新，不另建重复安装。

链接到实体目录的安装，先保存并校验完整旧目录，确认目标与所有共用 profile。主线尚无受支持的共享实体目录更新事务；只有具备针对该目标经过验证的原子交换及回滚方法，且能保持 profile 链接有效时才替换，否则暂停此端并保留原安装。连续执行两次普通移动不能视为原子交换。插件管理器管理的安装沿用官方更新路径，不直接覆盖它的缓存。

对更新后的实际实体路径运行：

```sh
python3 tools/verify-artifacts.py --verify-dsh-plugin /absolute/installed/azhou-agent-skin
```

再比对已安装完整文件树与本次候选摘要。完成条件：插件内容一致、原 profile 仍解析到预期目标、无重复安装；运行中的模块需重新加载后才能确认新版生效。

## 4. 实机复查与收尾

在已授权的本机范围逐端验证。先记录运行实例和用户工作状态；需要退出或重启时说明影响，当前执行会话所在的 Codex 放最后。没有执行重启就如实记录，不为统一显示“通过”而打断当前会话。

| 检查 | 通过标准 |
| --- | --- |
| 安装内容 | 实际安装摘要对应最终候选，来源和入口可核验 |
| 当前运行内容 | 页面/控制器实际载荷或构建身份对应已安装版本 |
| 冷启动 | 从安装入口启动，控制器就绪；另行观察动画完成和壁纸应用 |
| 热启动（Codex） | 再次打开激活同一实例，不重播、不重复注入 |
| 外观设置 | 保存、重新打开结果一致；测试值恢复并核验 |
| DSH 加载 | 实际目标 profile 加载新模块，宿主设置中的外观入口可用 |

Codex 的只读安装验收入口：

```sh
python3 -B tools/test-installed-acceptance.py --out .local/local-install/codex
```

冷启动使用同一工具的 `--cold-start`，前提是宿主已完整退出；工具不会自动退出运行中的宿主。没有 Dock 固定入口、未执行冷启动或缺少视觉审阅时保留 pending。整体非通过需要逐项解释，不能把 pending 改写成失败或全通过。

每轮在 Git 忽略的本地证据目录保留一份收据，至少记录：

- 源码提交、候选输入与产物摘要、宿主版本/指纹；
- 两端各自的目标、旧/新版本与摘要、安装结果、恢复位置；
- 是否重启/重载、实际运行版本、验证项与观察时间；
- 通过、失败、未执行项和剩余动作。

分别报告“文件已安装”“新版已加载”“实机已验证”。某端未完成不阻止报告其他端结果，但不能写“两端运行验收全部通过”。私有素材、截图、原始记录、回执和完整旧包留在本地，不提交到公开仓库。

安装来源仍绑定工作区时保留租约、构建载荷和回执；代码合并不等于可以回收来源目录。完成原生来源接管及安装复查后，才按工作区规则处理。备份保留到本轮恢复责任结束，后续清理以明确目标和有效恢复状态为依据。
