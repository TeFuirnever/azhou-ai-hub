# 最佳实践对标框架（Arch Doc review 模式）

两条评审线并行，各自打分并列发现；lead 合并成一份报告（总分 + 按严重度排序的发现 + 改进清单）。

## 结构线（对标：ISO/IEC/IEEE 42010、C4、arc42、SEI Views & Beyond、4+1、Nygard ADR、docs-as-code）

| 维度 | 核查问题 |
|---|---|
| 利益相关方-视图映射 | 承诺的视图与正文章节有无索引对应？viewpoint（记法/约定）有无最小声明？ |
| 视图间一致性 | 同一组件在不同章是否同名？Owner 词汇是否单一目录？ |
| 抽象层级 | 是否有低层实施参数占压架构正文？上下文图是否混入内部组件？ |
| 可追溯性 | 上游需求 → 架构章节 → 下位设计的双向追溯是否到条目级？ |
| 决策记录 | 重大决策是否有 ADR（Nygard 五段式）？「难逆转」的判定与实际是否一致？ |
| 质量场景规范性 | 场景是否达六元组（刺激源/刺激/环境/响应度量/验证/优先级）？判据是否可判定？ |
| 冗余与缺失 | 词汇表/视图索引/读者指南/ADR 是否齐？同一事实是否多处重复？ |

## 技术线（对标：SEI 质量场景、Microsoft STRIDE、AWS Well-Architected、Google SRE、渐进交付、AI-Agent 安全）

| 维度 | 核查问题 |
|---|---|
| 质量可测性 | 质量场景卡（六元组场景表）是否逐属性建立？响应度量是阈值/二元判据还是方法名？容量表有无目标值占位列与门限（警告/中断）语义？ |
| 威胁覆盖 | STRIDE 六类逐类有控制+验证？有无信任边界枚举与风险排序？有缓解无威胁定义 = 缺口 |
| 可靠性/运维 | SLI/SLO 占位？readiness review 有 Owner 与门禁语义？回滚/故障/备份演练有频率义务？ |
| 渐进交付 | feature flag / canary / 自动回滚触发器 / 回滚演练，四件套各覆盖？ |
| AI/Agent 风险 | eval 三件套（数据集/基线/通过线）是否版本化并有漂移阻断？记忆投毒是否入威胁表？guardrail 是否分层？身份引导链是否定义？ |
| 内部一致性 | 状态词是否受控？跨章引用是否闭合？目标态与现状是否混排？ |
| 生命周期 | 每类资产有保留期/删除语义/配额/成本计量？删除是否为正式提交点？ |

## 报告模板

```markdown
# <文档> 最佳实践评审
## 总评（两线总分 + 一句话结论）
## 评分表（每维 1-5 + 一句依据）
## 关键发现（严重度排序：发现 / 对标依据（框架名+主张）/ 可执行建议）
## 可落地改进清单（动作 / 涉及章节 / 预期收益 / 工作量 S-M-L）
```

纪律：发现必须引用框架公开主张作依据；「文档自觉声明未完成」记为诚实而非达标；无 L 工作量项时注明可用小步修订解决。报告落盘到目标文档同目录 `REVIEW.md`（或仓库 `evidence/`），并在文档变更记录入账。
