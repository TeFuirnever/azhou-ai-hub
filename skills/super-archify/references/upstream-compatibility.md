## Accepted upstream-behavior notes at the pin

Eight review findings reported against the packaged bytes (2026-11-24) sit in files identical to the pin — `renderers/shared/svg-export.mjs`, `pr/build.mjs`, `pr/attach.mjs` (four sites), `modules/code-analysis/overlay/page.mjs` and `story/tool.mjs` are vendored byte-for-byte — and were accepted as upstream-behavior notes rather than patched here: a hub-side fix would turn upstream bytes into unrecorded deltas and move the defect out of upstream's view. Upstream owns this surface, and a future re-pin at a fixed upstream commit carries the fixes; re-check each item against the new pin and drop the ones upstream has fixed. Each item was read in the packaged source, and the review threads on the adopting pull request carry the reviewer's reproductions.

| Where at the pin | Behavior | Hub-layer guidance |
|---|---|---|
| `renderers/shared/svg-export.mjs`, `export-svg` publishing | The input's resolved path is checked for existence but never compared with the destination, and this exporter never establishes the input-aware `resolveOutputPath` guard the native renderer path uses, so an output path that is a symlink to the input JSON (reproduced in the adopting PR's review) overwrites the specification with SVG and reports success. | Pass an output destination that cannot alias the input; if the destination is a symlink, repoint it before exporting. |
| `pr/build.mjs`, story artifact paths | The story writes to `views/<story.id>` (defaulting to `walkthrough`) with no collision check against view ids, so a view named `walkthrough` — or any view whose id equals the story id — has its static SVGs overwritten by the story bake while the receipt keeps duplicate asset ids whose static-view hashes no longer match the files. | Keep view ids distinct from the story id (and from `walkthrough` when the story has no id), and re-check the receipt's asset hashes after a build that uses both. |
| `pr/attach.mjs`, sticky comment selection | `--target comment` selects the first PR comment whose body contains a pack block, without filtering by author, so when another participant has posted such a comment first the PATCH is directed at their comment — replacing their pack where editing is permitted, or failing where it is not. | Before attaching to a comment, confirm no other participant's comment carries the pack anchors; check the target comment's author before relying on the attachment. |
| `modules/code-analysis/overlay/page.mjs`, review snapshot rebuild | `renderAnalysisSnapshot` always loads `analysis.previous/findings.json` while PR-bound runs compare against `analysis/base/findings.json`, so rebuilding a captured PR analysis with its review makes the verification context return null and drops the verification controls from the returned and saved HTML. | After accepting or revoking a finding on a PR analysis, expect the rebuilt snapshot to lose the verification controls; the underlying findings and review state are unaffected. |
| `pr/attach.mjs`, final publication after upload | The build's head is checked only during preflight; the final body or comment write after uploads does not re-read `headRefOid`, so a push that lands mid-upload publishes the stale pack and reports success even without `--allow-stale`. | Avoid pushing to the PR while an attach is running; after a concurrent push, re-run the attach instead of trusting the reported success. |
| `pr/attach.mjs`, attachment preflight | The receipt's recorded asset digest is never compared with the file on disk: the token hash is recomputed from the current bytes and the Markdown body digest is checked, but an SVG edited after `pr build` is uploaded and published against the old receipt's revision metadata (reproduced in the adopting PR's review). | Rebuild after any diagram edit so the receipt and the files agree; attach does not notice SVG drift on its own. |
| `pr/attach.mjs`, final description publication | The final body is rebuilt from the preflight `originalBody`, so an edit made to the PR description outside the pack block while attachments are uploading is discarded when the pack is published (reproduced in the adopting PR's review). | Do not edit the PR description while an attach is in flight; re-apply the edit after the pack lands, or diff the description afterwards. |
| `story/tool.mjs`, code excerpt extraction | The excerpt reader always runs `git show` at `facts.repository.revision` (the repository head) and never consults the citation's own `source.revision`, so a source verified against `base_revision` is quoted from the head — different code presented as the verified evidence — and a source deleted at head fails the build (reproduced in the adopting PR's review). | When a walkthrough cites base-revision code, compare the excerpt with the cited revision yourself, or re-verify the citation at head before relying on the story's quotes. |
