# Research: zcode sqlite 会话存储实测 3.14.4（u1 store scout，#252）

> 日期：2026-10-06（Asia/Shanghai）
> 性质：只读结构侦察——schema、迁移史、聚合元数据；**未读取、未入仓任何会话正文**。路径与 ID 一律脱敏为模式；聚合口径全部来自 `count/group by`、JSON 键名/枚举值与 ID 长度直方图，不出现 `title`、`directory`、`path`、消息内容的明文值。
> 对象：ZCode.app **3.14.4**（macOS；`CFBundleShortVersionString` 3.14.4，`CFBundleVersion` 3.14.4.7912）的 CLI 存储 `~/.zcode/`，重点是本次新发现的 `cli/db/db.sqlite`。
> 方法：对活库以 `sqlite3 "file:...db.sqlite?mode=ro" ".backup <tmp-copy>"` 生成只读副本，之后全部查询只在副本上执行，活库零写入；副本 `PRAGMA integrity_check` 返回 `ok`。
> 关联：issue #252 u1；证据节 `docs/research/2026-10-06-cross-harness-execution-evidence.md` §3.1；前置研究 `2026-09-10-zcode-session-store-format.md`（3.11.2，no-go）。

## 结论（go/no-go）

**go（带四条强制边界）。** ZCode 3.14.4 的 `cli/db/db.sqlite` 是明文、结构化、逐轮次的会话转写存储：`session/message/part` 三层模型 + usage 观测表，SQL schema 由 22 条具名迁移管理、外键/索引/触发器完整、行级 data-model 版本可辨、副本完整性校验通过。2026-09-10 在 3.11.2 上的 no-go 前提失效：当时的"cli/db.sqlite 无表"测的是一个 0 字节遗留文件（本日实测仍为 0 字节、无表），真实库在 `cli/db/db.sqlite`——迁移时间戳最早 2026-06-19、最早会话创建于 2026-07-03，说明该库在 09-10 侦察时点已存在并有数据，只是不在那次探测的路径范围内。

本票只回答"存储格式是否可解析"，**不开适配器票**（#252 决定：go 之后另立）。若后续立项，以下边界必须随票携带：

1. **同源去重（最硬的一条）**：store 内已吸收 19 条 Claude 导入会话——19 个 bare-uuid `session.id` 与 `v2/sessions/*/claude-import-<hex24>.json` 的 `meta.taskId` 精确重合 19/19，且全部带正文。zcode 适配器必须按 `id NOT LIKE 'sess\_%'`（或等价排除键）剔除，否则与 Claude Code 适配器（直读 `~/.claude/projects/`）重复计数，触碰同源比较硬边界。
2. **会话基数语义**：1492 个 session 行中仅 298 是 `interactive`，1017 个 `subagent_child` + 177 个 `workflow_child` 是子会话（`parent_id` 已填 1194 行）。任何"会话数"统计必须按 `task_type` 过滤或按 parent 去重；hub 工作区实测 interactive 仅 27、subagent_child 261（合计 288）。
3. **JSON 层漂移**：SQL schema 稳定，但 `message.data` 内键名随 data-model 版本改名（见下文版本稳定性节）。读取必须用宽容键集并按 `session.version` 门控，不能对单一键名硬编码。
4. **空值语义靠约定**：`share_url` 全部是空串（不是 NULL）、`workspace_id` 全部 NULL，适配器不能以 `IS NOT NULL` 判"有值"。

## store schema（实测）

`PRAGMA`：`page_size=4096`、`journal_mode=wal`、`user_version=0`、`application_id=0`、`schema_version=1`；副本 `integrity_check=ok`。

应用表 23 张，按职责分四组：

- **转写三层**：`session`、`message`、`part`。
- **usage 观测**：`turn_usage`（1242 行）、`model_usage`（28044 行）、`tool_usage`（32702 行）。
- **会话过程**：`session_entry`（11734）、`session_input`（2855，排队输入台账，带 `delivery`/`status` CHECK 约束）、`session_target`、`session_task_link`（177，子会话挂到 workflow run 的层级链）、`todo`（2850）、`input_history`（100）、`permission`（0 行）。
- **运行时/工作流**：`local_setting`（38）、`workflow_definition/run/event/activity`（本机全 0 行）、`dwf_run`（35）/`dwf_node`（1970）/`dwf_event`（6402）/`dwf_actor`（232，dynamic workflow journal，由迁移 `0019_dwf_journal` 引入）。
- **元**：`schema_migration`。

核心三表（DDL 摘录，列名如实）：

```sql
CREATE TABLE session (
  id text primary key, project_id text not null, workspace_id text,
  parent_id text, slug text not null, directory text not null, path text,
  title text not null, version text not null, share_url text,
  summary_additions integer, summary_deletions integer, summary_files integer,
  summary_diffs text, revert text, permission text,
  time_created integer not null, time_updated integer not null,
  time_compacting integer, time_archived integer,
  task_type text not null default 'interactive',
  title_source text not null default 'first_input'
    check(title_source in ('default','first_input','generated','custom')),
  title_message_id text, time_title_updated integer, trace_id text);

CREATE TABLE message (
  id text primary key,
  session_id text not null references session(id) on delete cascade,
  time_created integer not null, time_updated integer not null,
  data text not null, sequence integer);

CREATE TABLE part (
  id text primary key,
  message_id text not null references message(id) on delete cascade,
  session_id text not null, time_created integer not null,
  time_updated integer not null, data text not null, sequence integer);
```

`message` 与 `part` 各带 `sequence` 自动回填触发器（按 session / message 内 max+1）与复合索引（如 `message(session_id, sequence, time_created, id)`、`part(session_id, message_id, sequence)`）。

**role 语义**：`message.data` 是 JSON 文本，顶层 `role` 实测枚举 `{user, assistant}`（11168 / 68069，合计 79237 全覆盖）。assistant 消息顶层含 `parentID`——**68069/68069 全部解析到同会话的 user 消息**，即一轮 = 一条 user 消息 + 一串以它为 parent 的 assistant 消息。正文不再落在 message 上，而在 `part.data`：实测 `type` 枚举与行数 `tool 80319 / step-start 67070 / step-finish 66425 / text 50953 / reasoning 32155 / timeline 789 / compaction 144 / file 13`（合计 297868 全覆盖）。`step-start/step-finish` 是模型调用边界，`tool` part 承载工具调用与结果。

**轮次观测**：`turn_usage` 以 `(session_id, turn_id)` 为主键，列含 `user_message_id`、状态机 `running/completed/error/cancelled`、首 token/耗时/各类 token 计数与错误字段；`user_message_id` 1240/1240 解析到 message 表（2 行为 NULL）。`model_usage` 记到 provider/model/attempt 粒度，`tool_usage` 记到单次工具调用粒度（含 `read_only/destructive/approval_status` 等）。注意 `turn_usage` 仅 1242 行（远小于消息数）：usage 观测由迁移 `0010_usage_observability` 引入，早期会话无回溯数据，适配器不能假设轮次账全量。

**ID 模式**：`session.id` 长度直方图与 `task_type` 一一对应——bare uuid（38 字符）×19 = 导入会话；`sess_<36>` ×279 与 bare 合计 298 = interactive；`sess_<51>` ×1017 = subagent_child；`sess_<57..58>` ×177 = workflow_child。`message.id`/`part.id` 为 `msg_`/`part_` 前缀、长度 49–80 不等（跨版本变化，不能假定定长）。

**directory 字段**：工作区绝对路径，1492/1492 以 `/` 开头，47 个 distinct（长度 12–93）；`project_id` 45 个 distinct，与 directory 近 1:1；`workspace_id` 全 NULL。`time_*` 均为毫秒 epoch。`share_url` 全部为空串；`path` 全部非 NULL。`title_source` 分布 `first_input 1271 / generated 197 / custom 24`。store 时间跨度：2026-07-03 至 2026-10-06（本日）。

## 版本稳定性线索

- **引擎版本谱系独立于 app 版本**：`schema_migration` 22 条具名迁移（`0001_base_session_store` 至 `0022_backfilled_session_reasoning`），记录 `id, checksum, app_version, time_applied`；`app_version` 从 0.2.0 走到 0.16.5，分三个落库批次（2026-06-19、2026-07-22、2026-09-18）。`session.version`（行级 data-model 版本）实测窗口：`0.15.0`（07-03 起）、`0.15.2`、`0.16.3`、`0.16.1`、`0.16.5`、`0.16.9`（09-19 至今）。ZCode.app 是 3.14.4，而存储引擎走 0.x 线——适配器应以迁移史/`session.version` 门控能力探测，不能以 app 版本推断 schema。
- **JSON 键漂移实证**：0.15.0 时代的 assistant 消息同时带 `modelID` 与 `modelId` 两套键（5787/5787）；0.16.9 时代只剩 `modelId`（18351 对 0），`variant`/`reasoningLevel` 在部分中间版本出现、两端为 0。顶层键集（仅键名）跨版本出现 `modelID/modelId`、`variant`、`reasoningLevel`、`planEnabled`、`contextSnapshot`、`modelSelection` 等增删。SQL 层一个 ALTER 都没加（0.15.0 之后 `session` 的变化全靠 CHECK 列与 JSON），说明**稳定性主要靠迁移纪律而不是 schema 不变**。
- 迁移命名风格（`NNNN_<描述>`）与 `checksum` 列表明升级走可校验迁移，适配器可按 `schema_migration` 最大 id 探测能力面。
- 活库持续写入：工单前提观测为 1461 会话/287 hub，本日实测 1492/288——两个快照都是对的，适配器与文档口径都不应硬编码计数。

## 同源去重：sqlite vs v2/sessions vs rollout

- **v2/sessions（claude-import）**：19 个文件的 `meta.taskId` 与 sqlite 内 19 个 bare-uuid `session.id` 精确重合（本地比对仅读 `meta` 键名与 taskId，未读 `messages[]` 正文）。即导入副本同时存在于文件层与 store 内，且 store 内版本**带正文**。zcode 适配器无论走哪条路都必须排除这 19 条；Claude Code 适配器从 `~/.claude/projects/` 直读仍是该内容的唯一正源。排除键：bare-uuid `session.id`（`NOT LIKE 'sess\_%'`）；`title_source='custom'` 不是可靠标志（原生 custom 还有 5 条）。
- **rollout**：不构成滚动窗口转写来源。键集与 09-10 一致、仍是 request/response 完整载荷（重、请求级而非轮次级）；本机两次观测（3.11.2 与 3.14.4）都只有个位数文件、均为活跃 dynamic-workflow actor 会话。当作诊断日志可以，当作会话数据源不行。
- **净结论**：zcode 原生会话数据的唯一合理来源是 `cli/db/db.sqlite`（排除导入行、按 `task_type` 过滤计数）；`v2/sessions` 与 `rollout` 都不进 zcode 适配器范围。

## 方法与边界

- 只读：`sqlite3 "file:...db.sqlite?mode=ro" ".backup <tmp>"` 取副本后仅查副本；活库零写入。所有查询为 schema 读取、`count/group by`、`json_each`/`json_extract` 取键名与枚举值、`length`/`substr` 做 ID 模式直方图；未 SELECT 任何消息正文、`title`、`directory`、`path` 明文值。
- `v2/sessions` 比对仅读 `meta` 键名与 `meta.taskId`，未读 `messages[]`；`rollout` 仅读首行键集与值类型，未读载荷。
- 单机单版本（macOS + ZCode 3.14.4/3.14.4.7912）；Windows/Linux 与其他版本未验证。JSON 键集已在本机 0.15→0.16 区间观测到改名，后续版本可能继续漂移。
- 本文档数字为 2026-10-06 单日快照；活库持续增长，计数会随时间变化。
- 本票不改 support-matrix、不改代码、不开适配器票；go 结论仅为后续独立适配器票提供输入。
