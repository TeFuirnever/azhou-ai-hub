# architecture-governance

本 Skill 仅用于当前项目。用户授权、项目 AGENTS.md 和实际宿主能力优先。

## 修改前

1. 根据任务、合同和测试列出打算修改的入口与模块；干净 diff 不能代替预期影响范围。读取根及目标目录的 AGENTS.md、当前实现和最近的合同。已有架构检查器时先运行基线；没有时明确采用人工检查，不声称存在 ZCode 的架构门禁。
2. 局部、已知合同的变更只读相关内容；跨模块、归属变更或合同不明时再扩展到公开接口、直接消费者、状态所有者、失败路径与测试，形成有界上下文。不要为局部修改通读全模块。
3. 明确每份可变状态的唯一所有者。其他组件通过合同读取或发命令，不能另存一份被当作权威的队列、缓存或状态。已有命令、服务、适配器能表达行为时复用它。
4. 为新文件及跨模块调用指定所属层、公开入口和允许的依赖方向，遵守本项目实际架构。纯计算与 IO、副作用决策与执行分开；不把 ZCode 的固定层名、四文件模板或“停用单测”规则移入本项目。
5. 异步、远端或流式变化先写出：输入 → 所有者 → 准入 → 状态转换 → 对外结果；补充事件顺序、租约/代次、幂等标识、过期结果处理、取消、重放/恢复和持久化时点。存在连续流与快照补偿两条路径时分别验证同一所有者与顺序约束。
6. 新行为或公开合同变化更新其现有权威记录；修复已定义行为补回归证据，纯重构只在合同变化时改文档。普通已授权设计选择不重复请示，产品语义不明时只暂停依赖该决定的部分。

## 修改后

- 检查新增依赖、消费者、替代入口和失败清理，区分基线缺陷与本次回归。新模块按当前项目登记机制接入；没有登记机制就记录人工覆盖边界，不创造一套平行架构系统。
- 若存在架构基线，只有经审查的有意调整才更新，不能为消除失败自动接纳违规。检查器通过只证明它管理的文件与规则，不证明未登记模块或运行时语义。
- 按项目要求执行验证，报告状态所有者、依赖边、时序假设、检查范围与未核实项。新改动或新风险才扩大/重复检查。

来源、适配边界和许可证见 [provenance.md](provenance.md)。
